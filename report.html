Conversion rules — knowledge base

These files are the entire brain of the Teradata→Snowflake pipeline. The Stage-3 (convert) and Stage-6 (explain) agents read all of them, every run. To change behavior, edit these files — nothing else.

Conventions:

  • TD = Teradata source form. SF = Snowflake target form.
  • Rule IDs (SYN-01, DT-05, FN-03, DEF-01, SEM-02, BTQ-01, …) are

cited in fix logs, reports, and the HTML. Keep IDs stable; append new rules, do not renumber.

  • Two distinct failure modes are handled separately:
  • Syntactic (SYN-*, DT-*, FN-*, DEF-*) — the construct does not

exist or does not parse on Snowflake, or is an outright bug in the source. Stage 3 converts/repairs these.

  • Semantic (SEM-*) — the converted SQL parses and runs but its *meaning*

has drifted from the Teradata original. Stage 3 corrects; Stage 6 explains.

  • BTEQ client layer (BTQ-*, 07_bteq_client.md) — .bteq inputs only.

Dot-commands and $-substitutions are not SQL; they are converted away into orchestration, never carried into the Snowflake output.

  • If a rule requires an assumption about the data model (e.g. how a PERIOD

column was split), the rule states the assumption and the converter emits a -- TODO(SME) marker at the point of use.

  • The output must be honest: every difference between the Teradata source

and the Snowflake output must trace to a rule ID or a fix-log entry.

Defect handling policy

Source files may contain bugs (legacy code, hand edits, truncated copies). The converter must not silently propagate OR silently fix them.

Policy

IDDefect classAction
DEF-01Duplicate column in INSERT list (same name twice)Remove the duplicate on both sides (INSERT list and matching SELECT position) so positions stay aligned. Log.
DEF-02Missing whitespace / typo breaking a keyword (ASalias)Repair to the obvious intent. Log.
DEF-03Unbalanced parenthesesRebuild the expression to the evident intent shown by sibling expressions; if intent unclear → SME. Log.
DEF-04Malformed function call (e.g., CAST((col, 0, 999) AS BIGINT))Infer intent from the argument pattern (here: COALESCE(col, 0) guarded cast). Repair, mark TODO(SME). Log.
DEF-05INSERT column count ≠ SELECT expression countFind the missing/extra position by aligning names. Missing expression → synthesize the most plausible one from sibling column patterns, mark TODO(SME). Extra → SME. Log.
DEF-06Alias ≠ target column nameNot a defect (positional). Normalize alias to target name for readability.

Fix log format

Every repair appears in a comment block at the top of the converted file:

-- FIX LOG (source defects repaired during conversion)
-- [DEF-01] line 72-73: duplicate column `sac_cd` removed from INSERT and SELECT
-- ...

Rule of thumb: the converted file must be honest — anyone diffing source vs output can trace every difference to a rule ID or a fix-log entry.

Semantic-equivalence rules & explanation policy — SEM-*

Converting syntax makes a script run on Snowflake. This file makes it mean the same thing the Teradata original meant, and defines the written explanation that Stage 6 produces for every script.

Principle

> A migration is only complete when the converted Snowflake statement is > provably equivalent to the Teradata source for every row, or every intended > divergence is documented and SME-approved.

The Teradata file in 00_input/ is ground truth. Where intent cannot be read off the source — because the source itself is ambiguous or defective — infer from sibling columns / naming conventions and flag every inference with TODO(SME).

Semantic risk catalogue

These convert cleanly and parse fine on Snowflake, but can change results. Each must be checked and, if present, corrected and explained.

IDRiskTeradata behaviorSnowflake behaviorRule
SEM-01Integer divisionINT / INT truncates toward zero/ returns a decimalIf truncation was the intent, wrap in FLOOR/TRUNC; else keep / and note that results now carry decimals. Check every division on integer columns (see FN-23).
SEM-02QUALIFY / dedup orderingROW_NUMBER ties broken by physical/AMP orderSame function, ties non-deterministicEnsure the ORDER BY fully determines the winner; if it does not, ordering drift is a real behavioral change → flag SME.
SEM-03CHAR(n) padding & comparisonBlank-pads to n; trailing spaces ignored in =No padding; 'A' <> 'A 'If any predicate or join compares CHAR columns, wrap with TRIM/RTRIM to preserve Teradata semantics (see DT-05).
SEM-04Timestamp / timezoneSession TZ; TIMESTAMP carries no TZTIMESTAMP_NTZ vs TIMESTAMP_TZ differ; session TZ default differsPin the session TIMEZONE; pick NTZ/TZ to match the source (DT-09).
SEM-05SET-table dedupCREATE SET TABLE silently drops full-row duplicates on INSERTCREATE TABLE keeps duplicatesSET vs MULTISET lives in the target's CREATE TABLE DDL — not in an INSERT-only script, so it cannot be inferred from the DML alone. Never assume. If the DDL is supplied, detect SET/MULTISET directly. If it is not, treat multiple INSERTs into one target — or a UNION/UNION ALL whose branches all write to one target — as a SET-dedup *signal, not proof*: raise an SME question ("Is <target> a SET table?") and classify SME. Only once SET is confirmed, port each INSERT as INSERT INTO tgt ( SELECT … EXCEPT SELECT * FROM tgt ) — never a single cross-branch UNION.
SEM-06Implicit cast / NULL in comparisonLenient implicit casts ('123' = 123 works)Strict; may error or mismatchMake casts explicit (TRY_TO_NUMBER, TO_CHAR); verify NULL handling in IN/= (see DT-14).
SEM-07NULL orderingNULLS FIRST default varies by directionSnowflake: NULLS LAST for ASC, NULLS FIRST for DESCIf an ORDER BY feeds a QUALIFY/TOP, a differing NULL position changes which row wins. Make NULLS FIRST/LAST explicit.
SEM-08Empty string vs NULLTeradata often treats '' distinctly, and CHAR padding blurs the lineSnowflake '' is a real empty string, not NULLCheck that NULLIF(x,'') intent survived the conversion.
SEM-09Aggregate over empty set / SUM NULLSUM of no rows is NULL in both, but downstream division differs—Confirm any COALESCE around aggregates matches the source's intent.
SEM-10Lookup / exchange-rate join directionAlias names can lie about direction—Verify join key direction against the Teradata source; a "cleaned up" alias can hide a real bug. Never rename an alias to "make it read right" without SME sign-off.
SEM-11BTEQ control flow removed.IF ERRORCODE <> 0 THEN .QUIT 8 aborts the job mid-scriptSnowflake has no equivalent; statements run independentlyRemoving a dot-command changes failure behavior. Record what the removed control flow guaranteed and where it must be re-implemented in the orchestrator (BTQ-*). Classify SME.
SEM-12Multi-statement request atomicityA Teradata multi-statement request succeeds or fails as a unitSplit statements each commit independentlyIf the source relied on all-or-nothing, say so and flag the transaction boundary for the orchestrator.

What Stage 6 must produce per script

06_explain/output/semantic_<name>.md — a plain-language account a reviewer can read without opening the SQL:

  1. Purpose — one paragraph: what the statement does in business terms

(source tables, target table, the grain of one output row).

  1. Clause-by-clause walk-through — for each major block (each CASE, each

JOIN, the final dedup): what it computes and *why*. Where the converted Snowflake differs from the Teradata source, say what the source would have done instead.

  1. Semantic checks table — every SEM-* risk: Present? Corrected how?

Equivalent to Teradata? (Yes / Yes-with-assumption / SME).

  1. Divergences from the original — anything intentionally *not*

bit-identical, with justification.

  1. Open SME questions — the TODO(SME) items, each phrased as a decision

for a human.

  1. Inline anchors — a fenced ``anchors`` block (see below).

This markdown is the source for the semantic panels in report.html.

The explanation is editable and embedded in the SQL

The Stage-6 markdown is the editable source of truth — the human reviewer enriches it before sign-off. Section 6, Inline anchors, is a fenced

`06_explain/annotate.py` uses to inject the explanation **as comments** into the
final SQL:

- Purpose (section 1) + Open SME questions (section 5) → a `SEMANTIC
  EXPLANATION` header block in the SQL.
- Each anchor `note` → a `-- SEM ▸ <note>` comment above the first SQL line
  containing its `MATCH text` (use a short literal that appears **verbatim** in
  the converted SQL).

Output is `03_convert/output/<name>_final.sql` (the pure
`<name>_snowflake.sql` is left untouched). Regeneration is idempotent — edit the
markdown, re-run annotate, and the SQL comments refresh. Only comments are
added, so the statement still parses; validate the result to confirm.

BTEQ client layer — BTQ-*

Applies only to inputs with the .bteq extension (and to any .sql file that happens to carry dot-commands). These are BTEQ scripts: ordinary Teradata SQL wrapped in a client/orchestration layer that is not SQL at all.

> Policy: convert away, do not preserve. Snowflake has no BTEQ. Every > BTQ-* construct is removed from the Snowflake output and its *intent* > re-homed in the orchestrator (Snowflake Tasks, Airflow, dbt, a shell wrapper — > whatever the target platform uses). This is the opposite of the sibling > snowflake2snowflake pipeline's SNZ-* "preserve as-is" policy; do not > confuse the two.

The mechanical masking used during validation is done by bteq_protect.py (wired into 04_validate/validate.py). Masking exists only so the validator can reach the real SQL in a .bteq control run — it never changes the file, and the residual-construct scan still runs on the raw text, so every dot-command is still reported as a SYN-09 finding.

IDConstructExampleConversion
BTQ-01Session / connection commands.LOGON tdprod/user,pwd, .LOGOFF, .SESSIONS 4Remove. Connection is the orchestrator's job (Snowflake connection profile / warehouse). Never emit credentials into the SQL.
BTQ-02Error control flow.IF ERRORCODE <> 0 THEN .QUIT 8, .QUIT, .EXITRemove from SQL; re-home in orchestration. Record what the guard protected. Raise SEM-11 — removing it changes failure behavior. Classify SME.
BTQ-03Labels & jumps.LABEL RETRY, .GOTO RETRY, .REPEAT 5Remove. Loops/retries become orchestrator retry policy or a Snowflake Task DAG. Always SME — the control graph must be reproduced deliberately.
BTQ-04File I/O.EXPORT FILE = …, .EXPORT RESET, .IMPORT DATA FILE = …Remove. Replace with COPY INTO <stage> / COPY INTO <table> against a Snowflake stage, or leave to the orchestrator's extract step. State the replacement in the migration report.
BTQ-05Formatting / display directives.SET WIDTH 200, .SET TITLEDASHES OFF, .SET SEPARATOR, .SET FORMATRemove silently. Presentation-only; no Snowflake equivalent and no semantic effect. Log as [AUTO].
BTQ-06OS escape / include.OS rm -f /tmp/x, .RUN FILE = other.bteqRemove. SME: an .OS call is external side-effecting work and a .RUN pulls in another script that must be migrated as its own unit. Name the referenced file in the analysis.
BTQ-07Substitution variables${LOAD_DT}, $1Convert to a bound parameter or a session variable ($load_dt / SET load_dt = …), or leave as an orchestrator-templated placeholder — but say which, explicitly. Never inline a literal value without SME sign-off.
BTQ-08Multi-statement requestStatements joined by ; submitted as one requestSplit into individual statements. Raise SEM-12 — Teradata's all-or-nothing semantics are lost; the orchestrator must own the transaction boundary.

Analyze stage (01_analyze)

  • Inventory every BTQ-* construct with line numbers, classified normally

(AUTO for BTQ-01/BTQ-05, SME for BTQ-02/BTQ-03/BTQ-06).

  • For every control-flow directive removed, note in the analysis **what the

script did on error** — that is the requirement handed to the orchestrator.

  • SQL *between* dot-commands is analysed normally.

Convert stage (03_convert)

  • The Snowflake output must contain no dot-command. validate.py fails the

file if one survives (SYN-09).

  • Add one FIX LOG line per removed construct citing its BTQ-* ID and the

source line, e.g. -- [BTQ-02] line 41: removed .IF ERRORCODE guard — abort-on-error moves to the orchestrator (see TODO(SME)).

  • Emit a -- TODO(SME) at the point where removed control flow used to sit, so

the reviewer can see what the orchestrator now owns.

Report stage (05_report)

  • State the counts, e.g. *"N dot-commands removed (BTQ-01/02/05); M require

orchestrator work (BTQ-02, BTQ-03)."*

  • List the orchestration requirements the migration hands off: retries,

abort-on-error, file export, script includes. This list is the deliverable the platform team needs.
